# Board for app testers, not code readers: change spec v1

Status: draft v1 · Issue: #11 · Profile: prototype · Size: M · Builds on #8 and #10

## 1. Problem
The owner's rule (2026-11-13): a non-technical user is like a UAT tester. They care about their app, its versions, and trying a version before it goes live. They never read code. Today every "See what's asked" button and card title opens a GitHub page, and the board never shows the app itself.

## 2. Goal
The board shows the user's app: a link to the live app, the list of versions, and a "Try it" button on each change that is waiting for them. Whatever the team asks is shown on the board in plain words. Nothing on the board opens GitHub.

## 3. Scope in
- Read the project's GitHub releases (versions) and deployments (live and preview links). Both are optional: a project with neither still shows the board.
- A preview link can also come from a team comment whose team-event has a `preview` field (for hosts that don't record deployments).
- Show the ask in the page; take GitHub links out of the page.

## 4. Scope out
Answering on the board (the Approve buttons are the next slice), changing what the team writes (the `preview` field is read if present; adding it to the team's contract is a separate change in the team's repo).

## 5. Acceptance criteria
- **AC1 Try it.** A waiting change shows a "Try it" button that opens its preview: the latest successful non-production deployment whose branch or commit matches the pull request, else the latest `preview` in its team comments. No preview, no button. Only `https` links are shown.
- **AC2 The ask, on the board.** Each "Waiting for you" card shows the message that asked, in plain text: no Markdown marks, no team header line, no hidden data, masked, at most 600 characters with "…" when cut. It ends with how to answer: "Tell Ella in your chat with her."
- **AC3 Your app.** A "Your app" section shows: the live link (latest successful production deployment) as "Open your app"; the live version (latest published release) with its date and first lines of notes; a version waiting to go live (a draft release) marked "Ready to go live, waiting for your OK"; up to 5 earlier versions. With none of these it says the app isn't online yet.
- **AC4 No GitHub on the page.** No link on the page points at github.com, in the board or the error message. (The sign-in and picker screens still link GitHub; that's where sign-in happens.)
- **AC5 Optional reads.** If releases or deployments can't be read, the rest of the board still shows, with no error.
- **AC6** #8's and #10's acceptance criteria still hold, except #8 AC1 and AC5's links, which this replaces: the data still carries them, the page doesn't show them.

## 6. Constraints (owner-stated only)
- The user never sees code. Plain words a 10-year-old could follow. Reads only; runs on the user's computer.

## 7. Non-functional targets
- At most 10 extra GitHub reads per refresh (one for releases, one for deployments, one for pull requests, up to 6 for deployment statuses, one spare), inside the same one-minute cache.
