# Settings and keys without opening GitHub: change spec v1

Status: draft v1 · Issue: #16 · Profile: prototype · Size: M · Builds on #10 and #11

## 1. Problem
The team's checks and the person's app need settings on GitHub (repository variables such as `SETUP_CMD`, and secrets such as an AI service's key). Today the person would have to find Settings, then Secrets and variables, then Actions on github.com. A newcomer never opens GitHub (owner, 2026-11-13).

## 2. Goal
Ella sets the settings she already knows from the chat (team kit, `gh variable set`). For keys only the person has, the board's "Settings and keys" page shows a box: paste, Save, done. Secrets are locked on the person's computer and never shown again.

## 3. Scope in
- Ella's list, `team-settings.json` at the project's root: `{ "settings": [ { name, kind: "secret"|"variable", why, get?, steps?, value?, make?: "random" } ] }`. Names only, never a secret's value. Written by Ella with the team kit.
- `GET /api/settings`, `POST /api/settings` and the page.

## 4. Scope out
Hosting providers' own settings (for example a host's environment variables), GitHub environment-level secrets, deleting a setting.

## 5. Acceptance criteria
- **AC1 The list.** The page shows each sensible entry of Ella's list with its plain-words `why`, whether it is set, and for unset ones a "Get it here" link (https only) and `steps`. Entries with a bad name (not upper case, or starting `GITHUB_`), no `why`, an unknown kind, or a repeated name are skipped, and the page says some of the list didn't make sense. No list: "Nothing to set yet."
- **AC2 Secrets stay secret.** A secret's value is typed in a password box, locked with the project's GitHub public key (libsodium sealed box) before it leaves the board's server, and sent once. The board never returns, logs or shows a secret's value; GitHub only tells it that the secret exists and when it changed. A saved secret can be replaced, not shown.
- **AC3 Variables.** An app variable shows its value and can be changed. A new one is created.
- **AC4 Checks' settings are read-only.** `TEAM_OWNER`, `TEAM_CHECKER`, `TEAM_RECEIPTS`, `LINT_CMD`, `SETUP_CMD`, `DOCS_BUDGET` show only set or not set, with "Ella fills this in". The server refuses to change them, and refuses any name not on Ella's list.
- **AC5 Make one for me.** A secret with `make: "random"` gets a button that saves a fresh random value (32 random bytes) without the person typing.
- **AC6 Plain problems.** No permission, an expired sign-in, an empty or over-long value, and GitHub being down each give one plain sentence; none repeats the value.
- **AC7 Only from the board's own page.** Saving obeys the same rules as other changes (this computer, same origin, JSON body). The demo shows a sample list and saves nothing.
- **AC8** #8, #10 and #11 still hold, except the footer, which now says the board changes the project only when you save a setting.

## 6. Constraints (owner-stated only)
- The person never opens GitHub and never pastes a key into a chat. Plain words a 10-year-old could follow.

## 7. Permissions
- With the GitHub command-line tool's sign-in (`repo` scope) nothing extra is needed.
- The board's GitHub App (not created yet, see #10 §8) needs, beyond read access to Issues, Pull requests and Metadata: **Contents: read** (to read Ella's list), **Secrets: read and write**, **Variables: read and write**. "Secrets: read" only lists names; GitHub never gives a secret's value back.

## 8. New dependencies
`tweetnacl` 1.0.3 (NaCl box) and `@noble/hashes` 2.4.0 (BLAKE2b for the sealed box nonce): small, audited, no dependencies. Node's own crypto has no XSalsa20-Poly1305 and no short BLAKE2b. Needs `deps-approved`.

## 9. Not tested
A real GitHub App token against github.com (the App doesn't exist yet). The lock is checked against libsodium (PyNaCl) and in the tests with tweetnacl.
